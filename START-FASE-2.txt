DECISIÓN: SIN BCCR

En Fase 1 se reservaron las variables BCCR_NOMBRE/EMAIL/TOKEN. En Fase 2 las eliminamos porque la API pública del Ministerio de Hacienda CR (api.hacienda.go.cr) ofrece tipo de cambio USD/EUR oficial sin registro, sin token y sin variables de entorno. Endpoints relevantes:

- GET https://api.hacienda.go.cr/indicadores/tc        → { dolar: {compra,venta}, euro: {colones,dolares} }
- GET https://api.hacienda.go.cr/indicadores/tc/dolar  → { compra: {fecha,valor}, venta: {fecha,valor} }
- GET https://api.hacienda.go.cr/indicadores/tc/euro   → { fecha, dolares, colones }  (FORMATO DISTINTO — ver detalles abajo)
- GET https://api.hacienda.go.cr/indicadores/tc/dolar/historico?d=YYYY-MM-DD&h=YYYY-MM-DD
- GET https://api.hacienda.go.cr/fe/ae?identificacion=3006696489 → { nombre, regimen, situacion, actividades }
- GET https://api.hacienda.go.cr/fe/cabys?codigo=... o ?q=texto

Límites: 20 req/seg en ráfagas, 10 req/seg sostenido. Implementá retry con backoff y cache (tablas tipo_cambio_cache + cedulas_cache). El padrón se cachea 30 días; el tipo de cambio del día se cachea hasta las 23:59 de ese día.

Como fallback gratuito de tipo de cambio si Hacienda falla:
- https://cdn.jsdelivr.net/npm/@fawazahmed0/currency-api@latest/v1/currencies/usd.json (sin key, hosted CDN)
- https://api.frankfurter.dev/v1/latest?from=USD&to=CRC (sin key)
- https://api.frankfurter.dev/v1/latest?from=EUR&to=CRC (sin key, para EUR)
Implementá el fallback solo si el endpoint primario devuelve 5xx o timeout dos veces consecutivas.

COMPORTAMIENTO REAL DE LA API DE HACIENDA (verificado en vivo 2026-05-17)

Estos puntos NO están en la documentación oficial pero los confirmé contra el endpoint real. Implementalos correctamente desde el inicio:

1) `/indicadores/tc/dolar` devuelve el TC del DÍA HÁBIL ANTERIOR, no el de hoy. Hoy es 2026-05-17 (sábado) y devolvió fecha "2026-05-16" (viernes). Esto es correcto: el TC oficial se publica al cierre del día hábil. Implicación: la herramienta `obtener_tipo_cambio` DEBE aceptar un parámetro `fecha` (la fecha de emisión de la factura) y devolver el TC vigente en ese día. NO asumir "hoy" siempre — si la factura es del 14 de marzo, hay que buscar el TC del 14 de marzo (o el último hábil anterior si el 14 fue domingo).

2) `/indicadores/tc/euro` tiene un FORMATO DISTINTO a `/indicadores/tc/dolar`. Devuelve `{ fecha, dolares: 1.162, colones: 529.42 }` — un solo valor, sin compra/venta separadas. `colones` es CRC por 1 EUR (= 529.42). `dolares` es USD por 1 EUR. El MCP debe normalizar la salida de ambas monedas al mismo shape antes de devolverla al motor:
   - Para USD: `{ moneda: 'USD', compra: 449.17, venta: 455.61, fecha, fuente }`
   - Para EUR: `{ moneda: 'EUR', compra: 529.42, venta: 529.42, fecha, fuente }`  (no hay spread documentado para EUR, usá el mismo valor en ambas)

3) `/indicadores/tc/dolar/historico?d=X&h=X` devuelve `[]` (array vacío) cuando la fecha solicitada es un día sin TC publicado (fines de semana, feriados). La herramienta DEBE retroceder día por día (máximo 7 retrocesos) hasta encontrar un TC válido. Si tras 7 días no hay nada, devolver error claro `TIPO_CAMBIO_NO_DISPONIBLE`.

4) `/fe/ae?identificacion=X` con cédula inexistente devuelve `{ code: 404, status: "Information no available..." }` con HTTP 404. La herramienta `validar_cedula` DEBE traducir esto a `{ encontrada: false, estado: 'no_encontrada' }` sin tirar excepción. El skill tax-iva.md ya contempla CEDULA_NO_REGISTRADA como motivo de revisión humana.

5) `situacion.estado` puede tener variantes que NO son "Inscrito":
   - "Inscrito" → mapeá a `estado: 'inscrito'`
   - "Inscrito de Oficio" → mapeá a `estado: 'inactivo'` Y conservá `situacion.mensaje` que explica el problema. El skill tax-iva.md debe marcar la factura como CEDULA_INACTIVA en este caso.
   - Cualquier otro valor → `estado: 'inactivo'` por seguridad.

6) El campo `actividades` es un ARRAY de objetos `{ estado, tipo, codigo, descripcion }`, no un string. Decisión para Fase 2:
   - En la tabla `proveedores`, el campo `actividad_economica TEXT` guarda SOLO la `descripcion` de la PRIMERA actividad con `estado: 'A'` (activa) y `tipo: 'P'` (principal). Si no hay ninguna principal activa, guardá la primera del array.
   - En la tabla `cedulas_cache`, agregá un campo nuevo `actividades_json TEXT` que guarde `JSON.stringify(actividades)` completo, para que el Asistente Contable de Fase 3 pueda consultar todas si las pregunta.
